- 공통 페이징 계산 및 이를 사용하는 게시판·공지·관리자·계정·업무 목록.
- 게시판·공지 요청 모델 변환과 기존 문자열 공통 유틸 재사용.

## Summary

- 이미 존재하는 convert, share.common.query, PageResponse, StringUtil을 확장한다. 신규 범용 프레임워크나 도메인 통합 없이 확인된 중복만 제거한다.

## Findings or Scores

1. `BoardMapper.xml`: UUID/PK 상세 조회와 좋아요·댓글 집계 컬럼이 반복된다. 목록과 건수의 작성자 검색은 각각 JOIN 컬럼과 EXISTS로 구현되어 조건 변경 시 불일치 위험이 있다. 프로필의 계정 키는 UNIQUE이므로 동일 EXISTS 조건으로 공유할 수 있다.
2. `NoticeMapper.xml`: 상세 조회 3곳, 요약 컬럼 2곳, 목록/건수 필터 2곳이 중복된다. 기존 statement ID를 유지하고 SQL 조각을 공유한다.
3. 7개 목록 처리에서 `Math.ceil` 기반 페이지 수를 반복한다. `PageResponse.of`로 모으고 정수 연산으로 큰 count의 정밀도 손실을 방지한다. 기존 int 응답 범위는 포화 처리로 유지한다.
4. `PageSortSearchVo`와 관리자 계정 목록 offset은 int 곱셈이다. 큰 페이지 입력이 음수/잘못된 offset이 되는 문제를 long 계산과 Mapper 파라미터로 수정한다.
5. `PageSortSupport`는 DB 의존성이 없는 기술 유틸이지만 infra-db에 있다. 기존 share.common.query로 옮기고 실제 사용처를 일괄 갱신한다.
6. 게시판·공지 서비스가 검색 VO를 조립하고 공지 저장 VO와 trim 처리를 직접 구현한다. 기존 convert와 StringUtil로 이동한다.

## 2차 개선 검토 (2026-10-25)

- 사용자 승인: "개선작업 문서정리하고 ㄱㄱ". Backend / HEAVY이며 아래 6개 개선을 포함한다.
- 관리자 게시글 목록은 카테고리/계정을 INNER JOIN하지만 건수는 게시글만 센다. 카테고리가 있는 글과 없는 글을 한 건씩 넣으면 목록 1건·건수 2건으로 재현된다. 연관 정보는 LEFT JOIN으로 보강하고 목록/건수의 삭제·검색 필터를 공유한다.
- 공통 페이징에는 최대 크기가 없다. 기본 page=1/size=20은 유지하고 초과 size는 100으로 보정한다. 대시보드 공지 limit도 기본 5/최대 100으로 맞춘다. 업무 기능의 기존 검증은 유지한다.
- 게시판·공지·관리자 회원/게시글·계정 목록에는 고유 보조 정렬이 없다. 기존 1차 정렬 뒤 내부 PK DESC를 붙여 동률 순서를 고정한다. 데이터 추가/삭제 중 OFFSET 페이지의 스냅샷 일관성까지 보장하는 변경은 아니다.
- 관리자 계정 목록은 응답에 쓰지 않는 비밀번호 해시와 OTP 비밀정보까지 로드한다. `AcctSmryVo`에 필요한 필드만 두고 목록 SELECT/Mapper/Convert를 전환한다. 인증·계정 상세 조회는 기존 모델을 유지한다.
- 게시글·공지 상세는 SELECT→UPDATE→SELECT를 수행한다. 삭제 제외 조건이 있는 조회수 UPDATE의 영향 행 수로 404를 판단한 뒤 상세를 한 번만 읽는다. 트랜잭션과 원자적 증가를 유지한다.
- 첨부 교체는 N회 파일 조회와 N회 INSERT를 수행한다. 순서를 보존해 UUID 중복을 제거하고 파일을 일괄 조회·검증한 뒤 기존 연결 삭제와 다중 행 INSERT를 수행한다. 빈 목록, 소유권 위반, 누락/삭제 파일, UUID 대소문자, 실패 시 롤백을 검증한다.
- 변경 파일과 완료 기준은 기존 실행 계획의 2차 항목을 따른다. DDL·프런트·운영 DB·배포·커밋은 제외한다.

### 2차 적용 결과

- 관리자 목록의 누락과 count 불일치를 수정하고 관리자 회원/게시글·계정 목록 필터를 공유했다. 관리자 회원 조회에서도 사용하지 않는 pwd 컬럼을 제거했다.
- 최대 조회 크기 100, PK 보조 정렬, 계정 목록 전용 모델, 상세 중복 SELECT 제거, 첨부 일괄 처리 6건을 모두 반영했다.
- 첨부 10개 교체에서 파일 조회·기존 연결 삭제·일괄 INSERT 총 3회 호출을 테스트로 확인했다. 상세 조회는 조회수 갱신 1회와 상세 SELECT 1회이며 게시글의 첨부/태그 조회는 별도로 유지한다.
- 회귀 테스트 159개 및 SQL 시나리오 35개를 통과했다. 동시 다중 연결·운영 데이터 실행 계획·실제 성능 수치 검증은 수행하지 않았다. 자세한 결과는 실행 계획의 2차 결과를 따른다.
