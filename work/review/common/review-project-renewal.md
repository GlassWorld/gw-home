- 사용자가 2단계 구현과 다크모드를 요청했다. 통합 조회·분류는 소유자 조건을 포함한 MyBatis 쿼리에서 처리하고 CRUD는 기존 트리 API를 재사용한다.
- 완료 시각과 트리 변경의 직렬화, 최하위 기준 지연 건수를 함께 정비한다. 상세 파일·API 계약과 검증 결과는 실행 계획의 2단계 기록을 따른다.
- 적용 결과: 기본 다크모드, 통합 내 할 일·기존 폼/쓰기 재사용·대시보드 요약, `cmpl_at` 추가 SQL, 기존 트리의 소유권·순환 방지·진행률 유지. 프런트 타입/빌드, API 테스트·빌드, 임시 PostgreSQL 런타임의 SQL 검증을 통과했다. 실제 DB 배포는 하지 않았다.

## 3단계 착수 검토와 결과

- 보고서 전용 기능 외에도 dashboard의 최근 보고·건수·업데이트, WorkUnit의 보고서 사용 빈도 정렬, 프로필 즐겨찾기에 의존이 있다. 함께 제거해야 삭제 후 호출·링크가 남지 않는다.
- `DailyReportMapper`는 주간보고 SQL도 포함한다. WorkUnitMapper의 보고서 사용 통계 갱신과 함께 제거하되 기존 컬럼·보고서/매핑 테이블·데이터는 보존한다.
- `WorkGitCommitClient`는 WorkGitService의 연결 테스트와 WorkUnitService의 커밋 조회에서도 사용하므로 유지한다. 보고서 전용 AI 생성 서비스·리소스·설정만 제거한다.
- 종료 링크는 인증이 필요한 내 할 일의 안내로 연결하고, 삭제된 API는 404 계약을 검증한다. 저장된 즐겨찾기는 읽기 필터와 선택적 경로 정리 SQL로 대응한다.
- 사용자가 3단계를 명시적으로 승인했다. 변경 파일 범위·데이터 보관·검증 결과는 실행 계획의 3단계에 기록했다. 보고서 런타임·메뉴·대시보드 의존은 제거했고 DB 데이터와 공용 Git은 보존했다.

### 페이지와 공통 동작 애니메이션 보완 (2026-10-25)

- 사용자 요청 범위에서 Nuxt 페이지 전환과 기존 공통 메뉴·모달·선택 목록·토스트에 Vue Transition을 적용한다. 버튼/메뉴 피드백과 펼침 영역은 공통 CSS를 사용하며 새 의존성을 추가하지 않는다.

- 공통 모션 토큰과 `prefers-reduced-motion` 처리를 함께 적용한다. 실제 화면에서 빠른 페이지 이동·재열기·모바일 메뉴의 PC 전환·Escape/Tab·축소 모션을 확인한다.
- 적용 완료: 타입 검사·분리 출력 빌드와 임시 API 브라우저 검증을 통과했다. 실제 transition 이벤트, 연속 페이지 이동·메뉴/모달/목록 재열기·포커스 복귀·토스트 재배치·동작 줄이기 설정을 확인했다. 상세 범위와 결과는 실행 계획의 애니메이션 후속 보완 기록을 따른다.

### 테이블 생성·적용 안내 보완 (2026-10-25)

- 후속 오류 대응: 사용자가 `DO $$ DECLARE missing_tables TEXT` 위치의 `unterminated dollar-quoted string`을 보고했다. 파일의 닫는 구분자는 존재하므로 클라이언트의 블록 분리 또는 부분 실행 가능성이 있다. 두 적용 파일의 사전 검사 블록을 일반 문자열 인용으로 바꾸고, 달러 인용을 해석하지 않는 문장 분리 환경을 격리 DB에서 검증한다. 데이터 정의·사전 검사·트랜잭션 범위는 유지한다.
- 후속 결과: 일반 문자열 인용으로 수정했다. 이전 구문의 분리 오류 재현과 수정본의 분리 실행·재실행·기존 데이터 보호를 추가해 총 12개 SQL 검증을 통과했다. 실제 DB 클라이언트 종류는 확인하지 않았고, 운영 DB 적용은 수행하지 않았다.
- 사용자 후속 요청에 따라 리뉴얼 DDL의 누락된 적용 경로를 보완한다. 개별 완료 시각·알림 DDL은 있지만 통합 적용 파일과 적용 상태 점검 SQL이 없고, README에 DB 준비 진입점도 없다.
- 현재 배포 설정에는 SQL 자동 실행이나 마이그레이션 도구 연결이 없다. 파일 저장·서버 재시작은 실제 DB 반영을 뜻하지 않는다. 접속 설정의 대상 스키마는 `home`이며 `public`에 잘못 생성하지 않도록 적용 파일에 명시한다.
- 기존 `docs/all-ddl.sql`의 선행 DROP은 데이터 보존 요구와 충돌한다. 삭제 구문을 제거하고 빈 스키마에서만 실행되는 참고용 생성 스크립트로 제한한다. 기존 DB는 전용 리뉴얼 마이그레이션을 사용한다.
- 변경 범위: `sql/ddl/work/project-renewal-migrate.sql`, `project-renewal-verify.sql`, 알림 DDL의 컬럼 설명, `docs/all-ddl.sql`, DB 안내·README·현재 작업 문서, 격리 SQL 검증. 신규 기능·테이블 설계 변경 없이 기존 승인 범위의 배포 누락을 보완한다.
- 검증 범위: 기존 데이터 보존, 재실행, 누락된 기반 테이블의 조기 실패, 트랜잭션 롤백, 스키마 분리, DDL 원본 동기화. 실제 DB 연결·배포·메일 활성화는 수행하지 않는다.
- 보완 결과: 통합 적용·확인 SQL, 생성/변경/보존 대상 표와 실행 안내, 알림 컬럼 설명을 반영했다. 참고용 통합 DDL은 삭제 구문을 제거하고 비어 있지 않은 `home`에서는 실행을 거부한다. 격리 DB 적용 검증 9개와 알림 회귀 13개를 통과했다. 실제 DB 적용 완료를 의미하지 않는다.

### 5단계 착수 검토 (2026-10-25)

- 사용자 승인에 따라 간트차트·완료 통계의 읽기 API와 모바일 다크 화면을 추가한다. 기존 TODO 쓰기, 완료 시각, leaf 진행률·날짜 분류를 재사용하며 메일 발송은 보류한다.
- 목록의 소유권·활성·leaf 분류 SQL을 공유한다. 일정 필터와 완료 기간 필터는 다른 의미이므로 API와 화면에서 구분하고, 통계의 현재 분모와 기간 완료 건수를 함께 명시한다.
- WorkUnit에는 직접 일정이 없으므로 전체 TODO의 알려진 날짜에서 범위를 파생한다. 미지정 날짜가 남으면 부분 일정으로 안내하고, 간트는 기간에 필요한 조상·행만 표시한다.
- 통계는 현재 유효 완료 기준이며 과거 실적을 복원하지 않는다. 완료 취소·삭제·트리 변경에 따라 수치가 변할 수 있다. 추가 차트 의존성 없이 CSS/접근 가능한 숫자·목록을 활용한다.
- 구현 결과: 읽기 API·공유 SQL·간트/모바일 일정 목록·완료 추이/현황·메뉴/즐겨찾기를 추가했다. 신규 스키마 없이 기존 완료 시각을 사용한다. 서버 132개 테스트·bootJar, 격리 PostgreSQL 집계 8개/알림 회귀 13개, 프런트 타입·빌드·날짜 테스트·4개 화면 폭 검증을 통과했다.
- 수정·추가 파일과 상세 검증은 실행 계획의 5단계 결과를 따른다. 기본 빌드 출력의 개발용 manifest 혼입은 분리 출력에서 재검증했으며, 6단계 전체 회귀·실제 DB/기기·운영 검증은 별도다.

### 현재 결정: 메일 발송 사용 보류 (2026-10-25)

- 사용자가 메일을 발송하지 않고 넘어가기로 했다. 구현과 과거 검증 기록은 보존하고 발송 스위치의 기본값 false를 유지한다. Microsoft 365/Gmail 실제 연결·인증정보 준비·메일 발송·Node 이식은 진행하지 않는다.
- 작업자, 수신 주소 확인 요청, SMTP 전송의 준비 상태 검사로 비활성 시 발송이 차단되는 것을 확인했다. 운영 환경이나 DB 설정을 변경한 것은 아니다.
- 실제 메일 수신은 현재 리뉴얼 완료 조건에서 제외한다. 5단계 간트차트·완료 통계를 구현했으며 아래 4단계 설명은 보존된 구현 기록이다.

### 4단계 착수 검토

- 후속 계정 확인: 정종태 / jjt90@genexon.co.kr을 발신·수신 모두 사용. Microsoft 365로 추정되는 MX를 확인했으나 테넌트 정책과 SMTP 권한은 아직 확인하지 않았다. 기존 SMTP 어댑터에 선택 가능한 Microsoft 365 OAuth 방식과 발신 표시 이름을 추가하고, 운영 권한 변경 없이 로컬 테스트로 검증한다.
- 후속 적용 결과: OAuth SMTP 어댑터·캐시/갱신·전송 전 토큰 실패 분류·UTF-8 발신 이름·개인 로컬 예제를 구현했다. API 전체 122개 테스트와 bootJar를 통과했다. 실제 운영 연결은 회사 관리자 정보와 메일함 권한 확인 후 적용할 수 있다.

- 기존 TODO 쓰기는 업무 행을 잠그지만 알림 작업자와는 잠금을 공유하지 않는다. 발송 직전 취소·완료와의 경합을 막기 위해 계정 단위 잠금을 먼저 획득하고 기존 업무 잠금을 유지한다.
- 기존 메일/스케줄러 구현은 없다. 설정·예약·발송 이력의 별도 테이블과 서버 작업자가 필요하며 SMTP 결과 불명은 자동 재시도하지 않는 정책을 적용한다.
- 설정 화면과 TODO 상세는 기존 feature·공통 UI를 확장한다. API는 인증 사용자의 소유 데이터를 UUID로 조회하며 수신 주소 확인 후 활성화한다. 상세 파일·정책은 계획의 4단계 착수 계약을 따른다.
- 적용 결과: SMTP 환경설정, 서버 요약/개별 발송, 수신 주소 확인, 시간대·DST, 원자적 claim·발송 전 별도 커밋, 제한 재시도·접수불명 보존, TODO 변경과 같은 트랜잭션의 예약 취소를 구현했다. 다크 모바일 설정·상세 예약·이력 UI를 기존 컴포넌트 구조에 조합했다.
- Java/HTTP/SMTP 테스트, 실제 Mapper SQL의 격리 PostgreSQL 실행, 프런트 시간 변환/타입/빌드, 로컬 fixture UI 검증을 실행했다. 상세 결과는 [4단계 계획 기록](../../todo/common/todo-project-renewal.md#4-정기-요약-메일과-개별-알림)을 따른다. 운영 DB와 SMTP는 아직 적용하지 않았다.

- 반응형 디자인, 공통 컴포넌트, 내 할 일 통합 조회·편집, 정기 요약 메일과 개별 알림, 간트차트, 완료 통계.
- 일일보고·주간보고의 개인·공개·관리자 기능과 전용 의존성 제거 계획.
- 기존 업무·TODO·프런트 리팩토링 문서의 현재 상태 정정과 계획 통합.
- 기존 Nuxt3·TypeScript·Spring Boot·MyBatis 구조, 인증·권한, 유지 대상 기능 보존.
- 최초 검토는 문서만 변경했다. 사용자 확인 후 1단계 프런트, 2단계 업무·TODO, 3단계 보고서 제거, 4단계 메일 알림을 구현했다. 실제 DB 접속·마이그레이션, 외부 수신자 메일 발송, 배포·커밋은 제외한다.

## Summary

- 기존 WorkUnit과 TODO 트리를 확장하는 것이 적절하다. 업무별 트리 CRUD·완료·진행률 계산은 이미 코드에 존재하지만, 여러 업무의 내 할 일을 모으는 조회와 완료 시각·메일 예약 저장 구조는 추가 설계가 필요하다.

## Findings or Scores

### 1. 공통 UI와 디자인 토큰을 재사용할 기반이 있다

- 근거: [app.vue](../../../gw-home-ui/app.vue), [공통 UI](../../../gw-home-ui/components/common), [main.css](../../../gw-home-ui/assets/styles/main.css).
- 헤더·사이드바·토스트·다이얼로그와 BaseButton·BaseModal·BasePagination 등이 존재한다. 앱 골격은 `app.vue`에 있으며 별도 `layouts` 디렉터리를 전제하지 않는다.
- 전역 색상·간격 계층과 화면별 장식 스타일을 함께 정비해야 한다. 현재 배경은 다중 그라데이션을 사용하므로 색상 변수 변경만으로 리뉴얼을 완료할 수 없다.
- 페이지는 조합, 공통 UI는 범용 표현, feature는 도메인 상태·동작을 맡는다. 기존 컴포넌트를 우선 확장하고 반복이 확인된 부분만 공통화한다.

### 2. 업무별 TODO는 구현되어 있으나 통합 내 할 일 화면은 아니다

- 근거: [WorkTodoBoardPage.vue](../../../gw-home-ui/features/work/components/WorkTodoBoardPage.vue), [WorkTodoController.java](../../../gw-home-api/src/main/java/com/gw/api/controller/work/WorkTodoController.java), [WorkTodoService.java](../../../gw-home-api/src/main/java/com/gw/api/service/work/WorkTodoService.java).
- `/work/todos`는 활성 업무를 선택하는 화면이고, 상세 트리는 `/work/todos/[workUnitUuid]`에서 관리한다.
- 기존 API는 `/api/v1/work-units/{workUnitUuid}/todos`에 묶여 있다. 모든 업무를 화면에서 하나씩 조회하는 방식 대신 소유자 조건을 포함한 통합 조회를 설계한다.
- 최하위 TODO만 직접 완료하고 상위 진행률을 최하위 완료 비율로 계산하는 규칙은 유지한다. WorkUnit 자체의 수동 상태와 TODO 파생 상태는 구분한다.

### 3. 완료 통계를 위한 시각 정보가 없다

- 근거: [tb_wrk_todo.sql](../../../gw-home-infra-db/src/main/resources/sql/ddl/work/tb_wrk_todo.sql), [work.types.ts](../../../gw-home-ui/features/work/types/work.types.ts).
- 시작일·마감일·상태·진행률은 있지만 완료 시각과 알림 예약 필드는 없다. `updated_at`은 수정 시각이므로 완료 시각으로 사용할 수 없다.
- 완료 시각 저장, 완료 취소 시 처리, 재완료 집계, 과거 완료일 미상 항목의 표시를 먼저 정해야 한다.
- 제안은 현재 유효한 완료 시각 기준의 통계다. 완료 취소·삭제·트리 구조 변경에 따라 과거 기간의 표시 건수도 달라질 수 있음을 명시한다. 불변 실적 이력이 필요하면 별도 이벤트 이력 설계가 필요하다.

### 4. 지연 건수와 날짜 기준을 통일해야 한다

- 근거: [WorkTodoService.java](../../../gw-home-api/src/main/java/com/gw/api/service/work/WorkTodoService.java)의 `toResponse`, `buildTree`, `recalculateNode`.
- 진행률은 최하위 항목 기준이지만 `delayedCount`는 지연된 부모·자식 모두를 센다. 통계 카드에서는 최하위 항목만 집계하도록 조정하고 트리 행의 지연 표시는 별도로 유지해야 한다.
- 현재 지연 여부는 `LocalDate.now()`로 판단한다. 내 할 일·메일·통계에서 같은 사용자 시간대와 기준 시각을 사용하도록 바꿔야 한다.
- 기존 최하위 상태는 완료 또는 할 일이며, 진행중은 주로 상위 집계 결과다. 새로 수동 진행중 상태를 도입한 것으로 가정하지 않는다.

### 5. 업무 일정은 TODO 일정에서 파생하는 안이 적합하다

- 근거: [tb_work_unit.sql](../../../gw-home-infra-db/src/main/resources/sql/ddl/work/tb_work_unit.sql), [TODO DDL](../../../gw-home-infra-db/src/main/resources/sql/ddl/work/tb_wrk_todo.sql).
- WorkUnit 자체에는 시작일·마감일이 없다. 간트차트의 업무 행은 하위 TODO의 날짜 범위로 계산하는 안을 우선 제시한다.
- 날짜 미지정·한쪽 날짜만 지정·단일 날짜 항목을 구별해야 하며, 데이터 없는 기간을 임의로 채우면 안 된다.
- 모바일 기본 표현은 일정 목록으로 제안하고 간트 보기를 선택할 수 있게 한다. 차트 내부 스크롤과 페이지 전체 넘침을 구분한다.

### 6. 메일은 서버 예약과 발송 상태 관리가 필요하다

- 조사 범위: `gw-home-api/src`, `gw-home-share/src`, API 의존성. 이 범위에서 JavaMailSender·메일 starter·`@Scheduled` 기반 발송 구현을 확인하지 못했다.
- 계정에는 이메일이 있으나 알림 동의·수신 설정·발송 이력 저장과 동일하지 않다.
- 정기 요약과 개별 알림 모두 DB에 예약·상태를 남기고, 서버 재시작과 복수 실행에도 같은 발송 건을 중복 처리하지 않도록 설계한다.
- 발송 직전에 소유권·설정·완료·삭제·예약 버전을 재확인한다. 외부 제공자가 접수했는지 불명확한 실패는 무조건 재발송하지 않는다.
- 특정 메일 제공자는 아직 정하지 않았다. 운영 발신 도메인·기존 SMTP 또는 API 계정 확인이 선행되어야 한다.
